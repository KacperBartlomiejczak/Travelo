# Task: Light / dark split, welcome polish, profile setup button and profile from Google / Discord
Status: in progress

## Understanding & assumptions
Kacper's request (2026-10-19), with screenshots: on a light phone the app mixes themes — the side panel is light, but the trip view (cover + cards) and the pill are dark. Light and dark must be separated. Plus two profile-setup changes.

**Part A — fixes (first):**
1. **Trip view follows the phone's theme.** Today it is always dark (`DarkThemeScope`, decision A4 of `trip-flight-tabs-name-cover`, now reversed). In light mode the cover photo fades into paper, the name and dates are dark text, the cards are light. Dark mode stays as it is.
2. **Pill follows the theme.** Today it is always ink (`pill-nav-and-dialog` D2, now reversed). In light mode: white pill, thin border, shadow, active item terracotta. Dark mode stays as it is.
3. **Welcome screen stays dark, but the photo is darkened over the full screen height** (today the fade into ink starts at 35 % of the height, so near the sign-in sheet's rounded corners the edge of the photo shows and looks bad). **Title, sentence and button get an entrance animation.**
4. **Profile setup: "Zapisz i zaczynamy" is disabled until the form is complete** — a nick that meets the rules (P1 of auth-onboarding) and at least 1 interest. The photo stays optional. A taken nick still shows only after the tap (no live check, P1).

**Part B — profile from Google / Discord:**
5. After signing in with Google or Discord, the profile setup starts **pre-filled** with the nick and photo from that account. E-mail sign-in has no such data — the form starts empty as today.

**Done when:** all of the above works, full suite + typecheck + lint green, verifier PASS per step, Kacper's device check of the manual steps passes, `Architecture.md` updated.

**Assumptions:**
- The photo viewer (`/trips/[tripId]/photos`) stays dark in both themes (a dark photo viewer is the norm; it is not part of the "mixed" look). *Kacper did not answer this explicitly — confirm with approval (P2).*
- Controls drawn over a photo keep their dark look in both themes: the round ☰ / ⋮ buttons (ink 50 %, light icon) and the photo-tile overlays. They must stay readable on any photo.
- The status bar over the cover stays light in both themes (as today), because the top of the cover is a photo, not paper.
- The snackbar stays inverse to its screen; with the trip view light it becomes dark there automatically.
- The loading skeleton follows the theme too (it is outside `DarkThemeScope` already).

### Proposals for Kacper to confirm with this plan (P)
- **P1 — Welcome darkening (my reading of D3):** a uniform ink layer over the **whole** photo at 50 % (`overlay.scrim`, the token already used behind sheets), and on top of it the existing fade to solid ink at the bottom (behind the text and the button). The photo is still visible, but dim everywhere; there is no bright part and no visible edge.
- **P2 — Photo viewer** stays dark in both themes.
- **P3 — Welcome entrance animation** (design-context §9): title, then sentence, then button; each fades in (opacity 0 → 1) and rises 16 dp (`translateY 16 → 0`), 240 ms ("standard transition"), enter easing `(0.2, 0.8, 0.2, 1)`, 80 ms between items. Runs once when the screen appears. **Reduced motion:** no movement and no fade — everything is shown at once (§9.4). Uses `react-native-reanimated` (already a dependency). The button is tappable from the start (the animation never blocks it).
- **P4 — Invalid form + keyboard "Gotowe":** does nothing (the same as the disabled button). The format / empty-nick error messages (D20 of auth-onboarding) are no longer shown, because the button cannot be tapped with a bad nick; the hint under the field ("3–20 znaków: litery, cyfry, _ i .") says what is needed. The "Wybierz co najmniej jedno." hint under interests stays. A taken nick still shows "Ten nick jest zajęty." after the tap, scrolls there and moves focus (D24).
- **P5 — Pre-filled, not automatic:** the nick and the photo from Google / Discord are only suggestions — the user can change the nick, replace the photo from the gallery, and still has to pick interests. Nothing is saved before "Zapisz i zaczynamy".
- **P6 — Nick suggestion:** taken from the account name and turned into a valid nick: lower case, Polish letters without diacritics (`ł → l`, `ą → a` …), characters other than `a–z 0–9 _ .` removed, spaces removed, leading characters removed until it starts with a letter, cut to 20 characters, no `..`, no trailing `.`. If the result is shorter than 3 characters, the field starts empty.
  - **Discord:** the Discord username (already lower case `a–z 0–9 _ .`, so usually unchanged).
  - **Google:** the full name, e.g. "Kacper Bartłomiejczak" → `kacperbartlomiejczak`.
  - If the suggested nick is taken, the user sees "Ten nick jest zajęty." after the tap, as today (no automatic digits added).
- **P7 — Photo suggestion:** the account photo is **downloaded once and copied** into our private `avatars` bucket on save, through the same path as a gallery photo (≤ 512 px, JPEG, no EXIF). No schema or migration change. If the user later changes the Google / Discord photo, the Travelo photo does not change. Larger size requested (Google `=s512-c`, Discord `?size=512`). Only `https` URLs from `lh3.googleusercontent.com` and `cdn.discordapp.com` are accepted; anything else is ignored. If the download fails, the circle stays empty (no error — the photo is optional), and the picker says "Dodaj zdjęcie". While it downloads, the circle shows a spinner; the button does not wait for it.
- **P8 — Google / Discord accounts without a photo** (default avatar): Discord's default avatar is not a custom photo — ignored; Google's default letter avatar cannot be told apart reliably, so it is taken as a photo. (Alternative: skip Google photos entirely — say if you prefer.)

## Approach
- **A1/A2 (theme):** surgical. The trip view stops using `DarkThemeScope`; `TripHero` and `CurrentTrip` take their background and text from the normal theme roles (`colors.background`, `colors.text.primary/secondary`) instead of `colors.hero.*`. `colors.hero.*` keeps its meaning: "dark, over a photo" (welcome, viewer, ☰ ⋮, photo tiles). `colors.nav.*` gets a light and a dark value (light: `neutral.0` background, `border.default`, `text.secondary` inactive, `brand` active; dark: today's values). No new tokens. *Rejected:* a new `tripHero` token group — more tokens for the same values the theme already has.
- **A3 (welcome):** one extra full-screen `Rect` with `overlay.scrim` under the existing gradient; entrance animation with Reanimated `useSharedValue` / `withDelay` / `withTiming` and `useReducedMotion`. *Rejected:* Reanimated layout animations (`entering={FadeInDown}`) — less control over the exact curve and harder to test.
- **A4 (button):** `disabled={offline || !ProfileSetupInputSchema.safeParse(...).success}`; the schema is the single rule. *Rejected:* a hand-written "is complete" check — duplicates the schema.
- **B (prefill):** a Zod schema parses the Supabase user's `user_metadata` (provider data is external input) into `{ suggestedUsername, avatarUrl }`; a pure function makes the nick; the screen reads the signed-in user from `useSession()`, pre-fills the nick and downloads the photo to the cache (`expo-file-system`, already a dependency) as the picker's `uri`. *Rejected:* storing the provider's URL in `profiles` — needs a migration, depends on Google / Discord servers, and Discord URLs break when the photo changes.
- **Source check (step 5):** the exact `user_metadata` fields Supabase fills for Google and Discord are read from the Supabase docs / `@supabase/auth-js` before writing the schema, and cited in the progress log.

## Data structures (Zod)
Only Part B adds schemas, in `src/schemas/auth.ts` (exported from `index.ts`). Field names to be confirmed against the docs in step 5:

```ts
// Raw identity data Supabase stores on the user (external input → parsed, unknown keys ignored).
export const ProviderMetadataSchema = z.object({
  full_name: z.string().optional(),
  name: z.string().optional(),
  user_name: z.string().optional(),        // Discord username (to confirm)
  avatar_url: z.string().optional(),
  picture: z.string().optional(),          // Google (to confirm)
});

// What the profile setup gets from it.
export const ProviderProfileSchema = z.object({
  suggestedUsername: UsernameSchema.nullable(),   // valid by P1 rules, or null
  avatarUrl: z.url({ protocol: /^https$/, hostname: /^(lh3\.googleusercontent\.com|cdn\.discordapp\.com)$/ }).nullable(),
});
export type ProviderProfile = z.infer<typeof ProviderProfileSchema>;
```
Pure functions (in `src/lib/provider-profile.ts`): `suggestUsername(name: string): Username | null`, `providerProfile(provider: 'google' | 'discord' | 'email', metadata: unknown): ProviderProfile`.

No change to `Profile`, `ProfileSetupInput`, migrations or SQLite.
