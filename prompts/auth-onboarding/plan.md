# Task: Sign-in and profile setup (auth-onboarding)
Status: in progress

## Understanding & assumptions
Today the app signs in **anonymously** on first launch. This task replaces that with a real account:

1. **Welcome screen** — "Witaj w Travelo", one sentence, "Zaloguj się" at the bottom.
2. **Sign-in** — a bottom sheet with "Kontynuuj z Google", "Kontynuuj z Discordem" (D13) and "Kontynuuj z e-mailem" (e-mail → 6-digit code from the e-mail).
3. **Profile setup** — on first sign-in only: a unique username (nick) first, then interests, and an optional profile photo from the gallery.
4. Then the app opens as today ("Podróż").

Every user gets a **6-character friend code**, generated by the server when the profile is created. It is **not shown anywhere yet**; showing it, the QR code and adding friends by code are the next feature.

**Done when:** a new user goes welcome → sign-in (Google or e-mail code) → profile setup → home; a returning user (profile exists) goes straight to home, also offline; no code path signs in anonymously; full suite, typecheck, lint and the SQL tests are green; Kacper's device run passes.

### Decisions (Kacper, 2026-10-18)
- **D1 — Sign-in methods:** Google and e-mail with a code. Facebook and phone (SMS) later.
- **D2 — Anonymous accounts:** removed. Sign-in is required. An anonymous session already on a phone is signed out locally on launch, so the welcome screen shows. Trips of anonymous accounts stop being visible (test data only). The phone's local copies (trips, chosen trip, pending budget changes) are cleared on sign-in, so one user never sees another's data.
- **D3 — Username:** a unique nick, checked on save.
- **D4 — Friend code:** generated now by the server, 6 characters from uppercase letters and digits without look-alikes (no `0 O 1 I L`), unique; not shown yet.

- **D6 — Buttons:** one "Zaloguj się" on the welcome screen opens a bottom sheet with the options; e-mail goes to its own screens (e-mail → code).
- **D7 — Required to enter the app:** the nick and at least 1 interest. The photo is optional. The setup cannot be skipped.
- **D8 — Sign-out:** not in this task (comes with the Profile screen). Testing another account needs clearing the app's data.
- **D9 — Offline:** the user's own profile is kept as a **read-only copy in SQLite** (like the trip list), so a signed-in user opens the app offline straight on "Podróż". This extends the offline read scope to the own profile only (CLAUDE.md "Decisions made" gets one line).

- **D13 — Discord (Kacper, 2026-10-18, after step 3):** Kacper turned on the Discord provider in Supabase and asked for a "Kontynuuj z Discordem" button in the sign-in sheet, between Google and e-mail. - **D14 — When the phone forgets the previous user's data (orchestrator, step 4 review, follows D2):** the local user data (`clearUserData`) is cleared whenever the app is **signed out**, before the welcome screen shows (the gate keeps the splash screen until the clear finishes), instead of right after a sign-in. Data is only written while someone is signed in, and every sign-in starts from the signed-out state, so the next user always starts empty. A crash between the sign-in and the clear cannot leave the old data behind. Offline, a copy may then be used without checking its owner (the step 4 deviation), because only the signed-in user's data can be on the phone. If the clear fails, the welcome screen does not show and the app offers "Spróbuj ponownie". *Approved by Kacper, 2026-10-18.*
- **D15 — One write queue for the phone's database (Kacper, 2026-10-18, during step 5):** expo-sqlite does not run the async calls of one database in the order they were issued. Its iOS queue is concurrent (`ios/SQLiteModule.swift:10`), Android uses `Dispatchers.IO` (`SQLiteModule.kt:30`), and its own docs say order is not guaranteed (`src/SQLiteDatabase.ts:126-134`). So a stale write could slip past the sign-out clear, and multi-statement transactions (`forgetTrip`, `clearUserData`) can interleave with other statements. Kacper chose a serial queue in JS inside `createLocalStore`:
  - every store method runs as one task to completion before the next one starts;
  - the user-epoch check runs inside the task, right before its first statement;
  - the epoch is bumped synchronously at the start of the sign-out (`leave()`) and again in `clearUserData`.

  Rejected: `withExclusiveTransactionAsync` for the clear only (it does not cover a write in flight), and accepting the window.

## Approach
- **Supabase Auth** for both methods, no new dependency:
  - Google: `signInWithOAuth({ provider: 'google', options: { redirectTo, skipBrowserRedirect: true } })` → `expo-web-browser` `openAuthSessionAsync(url, redirectTo)` → `exchangeCodeForSession(code)`. The client switches to `flowType: 'pkce'`, so tokens never travel in the redirect URL (only a one-time code). `redirectTo` = `expo-linking` `createURL('auth/callback')` (scheme `traveling://` in a dev build, `exp://` in Expo Go). Both packages are already installed. Docs: Supabase "native mobile deep linking" + "auth-google" guides (context7, 2026-10-18); the docs use `expo-auth-session` only for `makeRedirectUri` / query parsing, which `expo-linking` + `URL` cover.
  - E-mail: `signInWithOtp({ email, options: { shouldCreateUser: true } })` → `verifyOtp({ email, token, type: 'email' })`. The e-mail template must contain `{{ .Token }}` so it carries a code, not only a link.
- **Profile** in a new `profiles` table (one row per auth user). The friend code is generated in Postgres by a `before insert` trigger (random from the 31-character alphabet, retried on a unique collision), and the client is not allowed to set or change it (column grants).
- **Gate** with expo-router `Stack.Protected` in the root layout (exists in expo-router 57): signed out → `(auth)` group; signed in without a profile → `onboarding`; signed in with a profile → `(drawer)` and the rest. While the session or the profile is unknown, the splash screen stays.
- A `SessionProvider` holds the session state from `supabase.auth.getSession()` + `onAuthStateChange`. The profile is read through a `ProfileRepository` (Supabase + SQLite copy, in-memory for tests), like `TripRepository`.
- `ensureSession` no longer signs in: it returns the user id or throws `NotSignedInError`.

*Rejected:* native Google Sign-In (`@react-native-google-signin/google-signin`) — a new native dependency, and its free version cannot pass the nonce Supabase needs on iOS/Android (Supabase docs). The browser flow works in Expo Go and dev builds alike.

## Data structures (Zod)
New file `src/schemas/profile.ts`:
```ts
export const USERNAME_MIN = 3, USERNAME_MAX = 20;
export const UsernameSchema = z.string()
  .regex(/^[a-z][a-z0-9_.]{2,19}$/, 'validation.usernameFormat')
  .refine((v) => !v.includes('..') && !v.endsWith('.'), 'validation.usernameFormat');

export const FRIEND_CODE_ALPHABET = 'ABCDEFGHJKMNPQRSTUVWXYZ23456789'; // 31 chars, no 0 O 1 I L
export const FriendCodeSchema = z.string().regex(/^[ABCDEFGHJKMNPQRSTUVWXYZ2-9]{6}$/);

export const ProfileSchema = z.object({
  id: z.uuid(),                       // = auth user id
  username: UsernameSchema,
  friendCode: FriendCodeSchema,
  interests: z.array(InterestTagSchema).min(1),
  avatarId: z.uuid().nullable(),      // file <id>/<avatarId>.jpg in bucket `avatars`
  createdAt: IsoDateTimeSchema,
  updatedAt: IsoDateTimeSchema,
});
export const ShownProfileSchema = ProfileSchema.extend({ avatarUrl: HttpUrlSchema.optional() }); // signed URL
export const ProfileSetupInputSchema = z.object({              // the setup form
  username: z.string().trim().toLowerCase().pipe(UsernameSchema),  // empty → 'validation.usernameRequired'
  interests: z.array(InterestTagSchema).min(1, 'validation.interestsRequired'),
  avatarUri: z.string().startsWith('file://').nullable(),     // picked, not sent yet
});
```
New file `src/schemas/auth.ts`:
```ts
export const EmailSchema = z.string().trim().toLowerCase().pipe(z.email('validation.emailFormat'));
export const OtpCodeSchema = z.string().regex(/^\d{6}$/, 'validation.otpFormat');
export const EmailSignInInputSchema = z.object({ email: EmailSchema });
export const EmailCodeInputSchema = z.object({ email: EmailSchema, code: OtpCodeSchema });
```
Device only: the profile copy is `ShownProfileSchema` without `avatarUrl` (signed URLs expire; the image stays in expo-image's cache under `avatar:<avatarId>`).

**Server** (`supabase/migrations/<ts>_profiles.sql`):
- `profiles` — `id uuid pk references auth.users on delete cascade`, `username text not null unique check (username ~ '^[a-z][a-z0-9_.]{2,19}$' and username !~ '\.\.' and username !~ '\.$')`, `friend_code text not null unique check (friend_code ~ '^[ABCDEFGHJKMNPQRSTUVWXYZ2-9]{6}$')` (set by the trigger), `interests text[] not null check (cardinality ≥ 1 and ⊆ the 17 tags)`, `avatar_id uuid null`, `created_at`, `updated_at` (trigger).
- RLS `to authenticated`: select / insert / update **own row only** (`id = (select auth.uid())`); insert also requires a non-anonymous user (`auth.jwt() ->> 'is_anonymous'` is not `true`); no delete. Grants: `authenticated` select, insert `(id, username, interests, avatar_id)`, update `(username, interests, avatar_id)`; nothing for `anon`.
- Storage: private bucket `avatars`, JPEG only, 2 MiB; objects `<userId>/<uuid>.jpg`; insert / select / update / delete only in your own folder.
- SQLite v4: `my_profile_cache (id = 1, profile_json, cached_at)`.

## Risks & open questions
- **R1 — Existing data:** every trip created so far belongs to an anonymous user and becomes invisible after the switch (D2). Nothing migrates it.
- **R2 — E-mail limits:** Supabase's built-in mailer sends only a few e-mails per hour per project. Enough for testing; a custom SMTP is needed before real users (a later decision).
- **R3 — App Store:** with Google sign-in on iOS, Apple's guideline 4.8 expects "Sign in with Apple" too. Not in this task; needed before an iOS release.
- **R4 — Google OAuth consent screen:** in "testing" mode only test users added in Google Cloud can sign in; publishing it is Kacper's step.
- **R11 — Discord accounts without a verified e-mail:** Supabase needs an e-mail from Discord. A Discord account without a verified e-mail fails to sign in; the sheet then shows the fixed Discord error. To check on the device (step 9).
- **R5 — Expo Go redirect:** `exp://` URLs change with the dev machine's IP; `exp://**` in the allow list covers it. A dev build uses `traveling://auth/callback`.
- **R6 — Anonymous JWTs still valid:** a phone that keeps an old anonymous session is signed out by the app on launch (D2), but the server would accept its token until it expires; disabling anonymous sign-ins stops new ones. The `profiles` insert policy additionally refuses anonymous users (`is_anonymous` claim), so they can never get a profile. The existing `trips` / `trip_members` / Storage policies do not check `is_anonymous`: an old anonymous token keeps working on its own trips until it expires (accepted; anonymous sign-ins are off and the app drops such sessions).
- **R8 — Nick enumeration:** a `23505` on save tells any signed-in user that a nick is taken. Inherent to P1 (accepted).
- **R9 — Avatar files on account deletion:** deleting an auth user removes the profile row (cascade) but not the files in `avatars`. A future account-deletion feature must remove them. An avatar upload that reached Storage but lost its answer also leaves a file nothing removes.
- **R10 — `23505` is ambiguous:** it can come from the nick, the primary key or (practically never) the friend code. Step 4 maps it to `UsernameTakenError` only when the error names `profiles_username_key`.
- **R12 — Unsynced budget changes at sign-out:** they are erased with the rest of the user's data (D2, D14). Today a sign-out happens only when the server revokes the session (no sign-out button, D8). Before the sign-out button is built, Kacper decides whether a last sync attempt comes first.
- **R13 — A hung SQLite call:** the serial queue (D15) has no timeout, so a native call that never returns would block every later store call (the gate would stay on the blank view). Not seen so far; a timeout is a possible follow-up.
- **R7 — Web preview:** OAuth redirect on web is not covered (phones only), like the SQLite caveat already listed in Architecture.md.
